Konzept · Entwurf v0.5 · 4. November 2026

plan-kit

Eine kleine Bibliothek aus Web Components, mit der Claude Code Pläne, Explorationen und Reviews als HTML schreibt – tokensparend, konsistent im Look und auf einen Blick lesbar. Dazu ein schlankes Entscheidungs-Log nach dem Vorbild von Architecture Decision Records (ADRs).

TL;DR
Der Agent schreibt nur semantische Tags wie <pk-option> oder <pk-decision>. Styling, Verhalten und Interaktion stecken in einer Lit-basierten JS-Datei, die versioniert von GitHub Pages geladen wird. Große Features werden nicht zum Megadokument, sondern zu mehreren verlinkten Seiten: eine Feature-Übersicht, darunter Phasen und kleine Aufgaben. Pläne sind kurzlebig – akzeptierte Entscheidungen wandern in einen decisions/-Ordner im Repo und bleiben. Ein Claude-Code-Skill beschreibt die Komponenten kompakt, damit der Agent sie zuverlässig nutzt.

Native zuerst: Das Kit stylt alle Standard-HTML-Elemente mit (<details>, <dialog>, <table>, <progress> …). Eigene Komponenten gibt es nur dort, wo HTML keine passende Semantik hat.

1. Problem

  • Markdown-Pläne werden lang und unübersichtlich → sie werden nicht gelesen, Architekturverständnis geht verloren.
  • Freies HTML ist lesbarer, kostet aber viele Tokens (CSS, Layout jedes Mal neu) und sieht jedes Mal anders aus.
  • Nach der Umsetzung ist der Plan wertlos – aber das „Warum“ hinter Entscheidungen geht mit ihm verloren.

2. Lösungsansatz – Optionen

A · Freies HTML

5. Eigene Komponenten (nur wo HTML nichts Passendes hat)

<pk-summary> – Kopf des PlansZiel, TL;DR, Status (draft/review/approved). Immer zuerst – in 10 Sekunden erfassbar.
<pk-decision> – Entscheidung (ADR-light) Feste Struktur in drei Teilen: Kontext (Situation, Rahmenbedingungen), Entscheidung (was und warum) und Konsequenzen (Folgen, Nacharbeiten, Folgeentscheidungen).
Attribute: id (z. B. webhook-idempotenz), status (proposed · accepted · superseded), date, optional supersedes / follows-up als Verweis auf andere Entscheidungen.
<pk-amendment> – datierter NachtragStatt eine Entscheidung zu überschreiben, wird neues Wissen mit Datum angehängt und als „nach der Entscheidung hinzugekommen“ markiert – z. B. Erfahrungen aus dem Betrieb oder geänderte Rahmenbedingungen. Grundlegende Änderungen = neue Entscheidung mit supersedes.
<pk-options> / <pk-option> – Lösungswege vergleichenKarten im Grid mit pros/cons-Attributen, selected markiert die Wahl.
<pk-code> / <pk-diff> – Code mit RandnotizenSprache per Attribut, <pk-note line="12" severity="blocking"> für Annotationen.
<pk-diagram> – Mermaid-WrapperInhalt = Mermaid-Code, Rendering lazy.
<pk-feedback> – „Copy as prompt“Sammelt Häkchen, gewählte Optionen, Kommentare und offene Antworten → ein Prompt für Claude Code.

6. So schreibt der Agent einen Plan

<script type="module" src="https://baesslerpa.github.io/plan-kit/0.1.0/plan-kit.js"></script>

<pk-summary status="review" goal="Stripe-Webhooks idempotent machen">
  Doppelte Events führen zu doppelten Buchungen. Fix über Event-ID-Tabelle.
</pk-summary>

<pk-options>
  <pk-option title="DB-Unique-Key" selected pros="einfach;robust" cons="Migration nötig"></pk-option>
  <pk-option title="Redis-Lock" pros="schnell" cons="neue Infra"></pk-option>
</pk-options>

<pk-decision id="webhook-idempotenz" status="proposed" date="2026-11-04">
  <h4 slot="context">Kontext</h4><p slot="context">Stripe liefert Events mehrfach aus.</p>
  <h4 slot="decision">Entscheidung</h4><p slot="decision">Unique-Key auf event_id in event_log.</p>
  <h4 slot="consequences">Konsequenzen</h4><p slot="consequences">Migration nötig; Folgeentscheidung zur Aufbewahrungsdauer.</p>
</pk-decision>

<aside data-kind="risk">Alte Events ohne ID im Backlog.</aside>
<aside data-kind="question">Wie lange Event-IDs aufbewahren?</aside>

<details>
  <summary>Technische Details</summary>
  …
</details>

<ol data-steps>
  <li><input type="checkbox"> Migration event_log anlegen</li>
  <li><input type="checkbox"> Handler prüft ID vor Verarbeitung</li>
</ol>

<pk-feedback></pk-feedback>

Die Überschriften und Absätze stehen als normales HTML in den Tags – ohne JavaScript bleibt alles lesbar.

7. Entscheidungs-Log: decisions/

Pläne sind kurzlebig, Entscheidungen bleiben. Deshalb trennt plan-kit beides:

  1. Im Plan entstehen Entscheidungen als <pk-decision status="proposed">.
  2. Nach Freigabe setzt der Agent sie auf accepted und legt pro Entscheidung eine Datei im Repo an: decisions/webhook-idempotenz.html – Dateiname als kurze Verbphrase, klein, mit Bindestrichen.
  3. Der Plan selbst darf danach veralten; das „Warum“ liegt dauerhaft neben dem Code und ist im Git-Verlauf nachvollziehbar.
  4. Spätere Erkenntnisse kommen als <pk-amendment> dazu; wird eine Entscheidung abgelöst, entsteht eine neue mit supersedes, die alte wird superseded.
Entscheidung: Ordnername „decisions“ statt „adr“ – verständlicher, und das Team legt dort eher auch Anbieter- oder Planungsentscheidungen ab.
Entscheidung: Bewusst ohne Governance, Rollen, Abstimmungen und schwere ADR-Templates – für ein 8-köpfiges Team zu viel Prozess.

8. Struktur großer Features: mehrere verlinkte Seiten

Statt eines Megadokuments oder Tabs nutzt plan-kit das, was HTML ohnehin kann: Links. Das folgt gängigen Praktiken aus spec-getriebener Arbeit mit Coding-Agenten – langlebige Spec und kurzlebige Pläne trennen, ein Ordner pro Änderung, Aufgaben klein schneiden.

plans/
  stripe-abos/
    index.html                 ← Feature-Übersicht (langlebig)
    phase-1-datenmodell/
      index.html               ← Phasen-Übersicht
      abo-tabelle-anlegen.html ← Aufgabe: Spec + Plan + Fortschritt
      migration-bestandsdaten.html
    phase-2-webhooks/
      …
    phase-3-app-ui/
      …
decisions/
  webhook-idempotenz.html      ← bleibt, auch wenn plans/ veraltet
EbeneInhaltLebensdauer
Feature-ÜbersichtZiel, Warum, Scope und Nicht-Ziele, Liste der Phasen mit Status und Links, Verweise auf Entscheidungen. Kurz – nur das Was und Warum, keine Umsetzungsdetails.So lange das Feature lebt
PhaseAbgeschlossener, auslieferbarer Zwischenstand (z. B. Datenmodell, API, UI); Reihenfolge und Abhängigkeiten der Aufgaben.Bis die Phase fertig ist
AufgabeKurze Spec, Umsetzungsplan, Schritte zum Abhaken, Risiken und offene Fragen.Bis zum Merge
EntscheidungKontext, Entscheidung, Konsequenzen (siehe oben).Dauerhaft

Regeln für den Zuschnitt

  • Eine Aufgabe = ein Bereich, eine Session. Was Datenbank, API und Frontend anfasst, sind drei Aufgaben.
  • Reviewbar in etwa zehn Minuten: Lässt sich der Diff nicht in dieser Zeit verstehen, war die Aufgabe zu groß.
  • Klare Ein- und Ausgaben pro Aufgabe, damit eine neue Session sie ohne Vorwissen umsetzen kann.
  • Bei Bedarf getrennt nach Bereich, z. B. eigene Aufgabenseiten für Backend und Frontend.

Navigation – nativ

  • Jede Seite hat oben eine Brotkrumen-Navigation als <nav aria-label="Pfad"> mit normalen Links: Feature › Phase › Aufgabe.
  • Übersichten listen Unterseiten als <ol> mit Links und data-status="todo | doing | done"; das Kit zeigt daraus Status-Badges und einen <progress>-Balken.
  • Links zu Entscheidungen auf decisions/… werden automatisch als Entscheidungs-Verweis mit Status angezeigt.
Entscheidung: Mehrere verlinkte Dateien statt Tabs oder einem langen Dokument. Jede Datei bleibt klein, einzeln reviewbar und kann einer neuen Agenten-Session gezielt mitgegeben werden.

9. Skill für Claude Code

  • SKILL.md mit Komponenten-Referenz in Kurzform (Tag, Attribute, ein Beispiel) – Ziel: unter 1.500 Tokens.
  • Regeln: immer mit <pk-summary> beginnen, Details in <details>, offene Fragen nie im Fließtext verstecken, kein eigenes CSS, Inhalte als normales HTML in den Tags.
  • Native zuerst: Erst ein Standard-HTML-Element wählen; ein pk--Tag nur, wenn es in der Referenz steht. Keine selbstgebauten Klapp-, Dialog- oder Fortschrittselemente.
  • Größe prüfen: Kleine Änderungen bekommen eine einzelne Aufgabenseite; größere Features die Ordnerstruktur aus Feature-Übersicht, Phasen und Aufgaben. Nach jeder erledigten Aufgabe den Status in den Übersichten nachziehen.
  • Vor dem Planen bestehende Einträge in decisions/ lesen und nicht stillschweigend widersprechen; nach Freigabe akzeptierte Entscheidungen dorthin schreiben.
  • Passt zu den bestehenden Pair-Skills (pair-feature, pair-bugfix, walkthrough): deren Pläne/Walkthroughs als plan-kit-HTML ausgeben.

10. Risiken & offene Punkte

Risiko: GitHub Pages nicht erreichbar → kein Styling. Gegenmittel: Pläne bleiben dank Progressive Enhancement lesbar; Inline-Build fürs Archivieren/Teilen.
Risiko: Breaking Changes an Komponenten. Gegenmittel: SemVer + Version immer im Pfad pinnen.
Risiko: Sehr neue Features (Invoker-Commands, Animation von <details>) fehlen in älteren Browsern. Gegenmittel: Sie verbessern nur, die Grundfunktion bleibt; Fallback-Skript nur für Dialog-Öffnen.
Risiko: decisions/ verwaist, wenn niemand Entscheidungen überträgt. Gegenmittel: Der Skill macht das Übertragen zum festen letzten Schritt.
Risiko: Status in den Übersichten läuft den Aufgaben hinterher. Gegenmittel: Skill-Regel zum Nachziehen; später eventuell ein kleines Skript, das den Status aus den Aufgabenseiten einsammelt.
Offen: Sollen plans/ nach Abschluss im Repo bleiben, archiviert oder gelöscht werden?
Entscheidung: Lit statt React – kein Build-Schritt für Konsumenten, kleine Bundle-Größe.
Entscheidung: Native HTML-Elemente haben Vorrang und werden vom Kit mitgestylt. pk-section, pk-steps, pk-risk und pk-question entfallen zugunsten von <details>, <ol> mit Checkboxen und <aside>.
Entscheidung: Hosting auf dem firmeneigenen Asset-Server/S3 statt öffentlichem CDN – Unabhängigkeit vom Anbieter. (abgelöst, siehe unten)
Entscheidung (4. November 2026, löst die vorige ab): Hosting erst einmal auf GitHub Pages (https://baesslerpa.github.io/plan-kit/<version>/). Das Repo ist ohnehin öffentlich, es kommt kein weiterer Anbieter dazu, und es braucht keine Zugangsdaten. Ein Workflow baut bei jedem Versions-Tag alle Versionen neu, die Version bleibt im Pfad. Das S3-Deploy-Skript bleibt als Ausweg, falls wir doch umziehen. Direkt aus dem Repo (raw.githubusercontent.com) geht nicht: falscher MIME-Typ, Browser verweigern das Modul.
Entscheidung: Lesbarkeit ohne JS ist nice to have, wird aber von Anfang an mitgedacht, weil es kaum Aufwand kostet.

11. Roadmap

  1. MVP: Classless-Basis-Stylesheet für native Elemente (details, aside, ol mit Checkboxen, table, dialog, progress), dazu summary und decision – Repo, Deployment auf GitHub Pages, Skill.
  2. decisions/-Workflow im Skill, amendment, options; Ordnerstruktur für große Features mit Brotkrumen-Navigation und Status-Übersichten.
  3. code/diff mit Notizen, diagram, feedback / „Copy as prompt“, Fortschritt speichern.
  4. Inline-Build, Dark Mode, eventuell Tabs; später: Verifikations-Agent prüft Code gegen decisions/.
